What was measured

On 26 November 2026 the reduction probe (reduce.py v0.1.1) ran with one command, reduce.py --device cuda --side 2048, on two rented data centre GPUs from two vendors: a single-VF partition of an AMD Instinct MI300X with PyTorch 2.15.0+rocm10.2.0, and an NVIDIA A100 80GB PCIe with PyTorch 2.8.0+cu129 on CUDA 12.9. The probe takes a sum, a mean, a running sum, row sums and column sums in fp32, fp16 and bf16, three runs each, and checks every result against a float64 reference: exactly where the true answer is exact, and inside a proven rounding-error bound otherwise.

On each card 25 of the 27 steps were clean. The two that were not are the same two on both cards: the running sum, torch.cumsum, over 8,388,608 elements in the two 16-bit formats. The same probe at the same length on the host CPU of the MI300X machine passed both. From the result files mi300x_reduce.jsonl, a100_reduce.jsonl and mi300x_cpu_cumsum_control.jsonl:

The values themselves

A ratio against a bound does not show what a user would see, so a short script read the numbers directly on a third card, a rented NVIDIA L40S with PyTorch 2.8.0+cu129. Its output is l40s_cumsum_check.txt.

On the first 16 fp16 inputs, the CPU and the GPU results of torch.cumsum differ at 12 of the 16 positions, from the fifth on. At the sixteenth, where the inputs nearly cancel, the true sum is 0.00665283. The CPU returns 0.00665283. The GPU returns 0.00732422, about 10% away. In bf16 the two differ at 5 of the 16 positions, from the tenth on, and at the sixteenth the CPU returns the true 0.01904297 and the GPU 0.01953125.

Adding the same 16 values one at a time on a CPU, with the running total kept in the 16-bit format, gives 0.00732422 in fp16 and 0.01953125 in bf16, the GPU's values exactly. Passing dtype=torch.float32 to torch.cumsum on the GPU and converting the result back made it match the CPU at all 16 positions and at all 1,024 of a longer prefix, in both formats.

What that does and does not say

The verdict word for these steps, outside-error-bound, is defined on the method page as all runs agreeing with each other but sitting outside the proven bound: a faulty unit, or a device accumulating below FP32. The measurements point to the second. Two cards from two vendors sit 61.3 times outside the fp16 bound at the same element, every repeat is bit-identical, and the value a third card returned at that element is the one a 16-bit running total produces. A faulty unit does not reproduce on another vendor's card.

So this is not a hardware fault and it is not particular to AMD or to NVIDIA. It is how the running sum is computed on the GPU path of these PyTorch builds: the total is kept in the 16-bit input format, where the CPU path returned the correctly rounded value on these short inputs.

It does not say that half precision is unsafe in general. Sums, means, row sums and column sums in fp16 and bf16 passed on both GPUs, and so did the matrix multiplies and transformer kernels in each card's published row. It also leaves two things open. The counts of results outside the bound and the bf16 worst cases differ between the two cards, and that difference is not explained. And at the full 8,388,608 length, the L40S check with dtype=torch.float32 still differs from the CPU at 131,533 fp16 positions; a separate CPU-only check put the first place the CPU's own fp16 running sum leaves the correctly rounded value at about element 4,500, so the short prefixes are the clean comparison.

Why a second run cannot catch it

A common guard against a wrong result from an accelerator is to compute it twice and compare. Here every repeat on the same device returned the same bits, so that guard passes. What separated the two answers was a second implementation: the CPU, or the same call with a wider accumulation type.

The hardware's own error reporting has nothing to add either. On the A100 the error counters could be read, and every one stayed at zero while the probe counted 7,836 results outside the bound across the two steps, which is the expected reading when nothing in the hardware went wrong.

Code that takes a running sum of half-precision values on a GPU, and cares about the result where the values nearly cancel, can pass dtype=torch.float32 and convert back.

Where it stands

It is reported to PyTorch as issue #206762, which asks whether accumulating in the input type on CUDA is intended, and suggests a note in the documentation if it is. An earlier PyTorch issue, #74438, covers the same class of difference for sum and mean.

The reduction probe is not yet part of chip-integrity run, so these files sit in results/evidence/ rather than in the chip tables.
