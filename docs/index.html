LEARN, PART 1 OF 5

What a silent error is

When a chip fails, there are three ways it can tell you. Only two of them are loud.

It crashes

The job stops. Annoying, but you know. Nothing is quietly wrong.

It raises an error

Memory with ECC, for example, notices a flipped bit, corrects it or reports it. Monitoring sees a counter go up.

It gives a wrong number

The job finishes. Every status light is green. One number in the output is wrong, and nothing on the chip knows. That is a silent error.

Where silent errors come from

A modern AI chip has tens of thousands of arithmetic units and billions of memory cells, made on a process so fine that a few atoms decide whether a transistor switches on time. Most units are perfect. A few are marginal: they work at one temperature and fail at another, work on most inputs and fail on a specific bit pattern, or degrade as the chip ages. When a marginal unit produces the wrong bit during a multiply, nothing compares the answer to the truth, so the wrong number simply flows onward.

The difference between a healthy and a marginal unit can be one bit: far below what anyone notices in a single number, and enough to change a model's output after a billion more multiplies.

Why the usual tests miss them

Vendor diagnostics run a fixed stress pattern for a short time and look for crashes and error counters. The research on real fleets says that is not enough. ByteDance's team reported that screening GPUs with synthetic microbenchmarks missed over 60 percent of the units that later corrupted real training runs, because the faults depend on the data being processed, show up with age, and are specific to individual units. A test that exercises one pattern for a few seconds can pass a chip that fails on the next pattern an hour later.

LEARN, PART 2 OF 5

Why it matters

One wrong number is harmless. The problem is scale: thousands of chips, billions of operations a second, and nothing that checks the answers.

Training runs go quietly wrong

In large language model training, a corrupted gradient from one faulty GPU spreads to every other GPU at the next synchronisation. The loss curve wobbles, days of compute are lost, and the cause stays invisible until someone finds the one unit. The second OSDI 2026 study below counted 18 such incidents and 13 faulty GPUs across 35 million GPU hours.

Inference answers drift

A serving fleet with one marginal chip produces slightly different answers from that chip, forever. No crash, no alert, just a share of users getting worse results.

The used GPU market has no condition test

Second-hand accelerators are bought and sold on model name and hours of use. Age is the biggest risk factor for silent faults, and there is no open, shared way to test a used card before paying for it.

Lenders cannot inspect the collateral

Loans are secured against GPUs. A jet has maintenance records and an inspection standard; a GPU has a serial number. An open integrity test is the first step towards a condition grade anyone can verify.

How a chip is tested here

Six probes so far, numbered as on the roadmap. Probe 1 makes the chip multiply matrices and judges every output element. Probe 2 fills the chip's memory with known values and reads every one back. Probe 3 checks the other kernels inside a transformer the same way as probe 1. Probe 6 has the chip compute checksums inside the same multiply, so a wrong element can be caught and located without any reference. Probe 9 feeds the matrix multiply inputs built to reach particular bits. Probe 11 reads the chip's own error counters around every run and asks whether the hardware noticed. Each probe has two independent checks, so a fault has to hide from both.

Probe 1: compute

The chip multiplies two fixed matrices, A and B, fifty times at each of three shapes and four precisions, plus FP8. Two checks run on every output.

The checks are independent. A large error fails the reference check. A tiny one, even a single bit, fails the repeat check because the first run and the later run no longer match.

The reference check, in plain words

Floating point arithmetic rounds at every step, so two correct computers can legitimately differ in the last digit. The question is how different they are allowed to be. Numerical analysis has a proven answer: for a dot product of length K, the rounding error can never exceed a bound that depends only on K, the precision and how the hardware rounds. Every element of the chip's result is compared with a float64 reference and must sit inside that bound. For int8 the arithmetic is exact, so the bound is zero.

|C − R| ≤ acc + u_out·(|R| + acc)
acc = g·(|A|@|B|)
g = n·u / (1 − n·u)
fp32: n = K, u = 2⁻²⁴
fp16, bf16: n = 2K, u = 2⁻²³
u_out: 2⁻²⁴ fp32, 2⁻¹¹ fp16, 2⁻⁸ bf16
int8, FP8: exact, bound 0

fp32 runs on the FP32 fused multiply-add units with TF32 off. fp16 and bf16 run on tensor cores, which round by truncation rather than to nearest and add in blocks, as Fasi, Higham, Mikaitis and Pranesh measured, so they get the wider allowance. Every fp16 and bf16 row published so far passed a bound four times tighter than this one. An element outside the bound is a wrong answer, not a difference of opinion about tolerance.

The repeat check, in plain words

The same inputs through the same chip should give the same bits every time. Run 0 is kept, and every later run is compared bit for bit. This catches an intermittent fault far too small to leave the bound, because the two runs simply no longer match. On the chips measured so far every run matched, which is itself a useful fact: the matrix kernels on these chips are deterministic.

Probe 2: memory

The matrix multiply touches a few megabytes. Most of an 80 GB chip is memory, and a bad row or a stuck bit there corrupts whatever lands on it. The memory probe fills most of the device memory, writes a known value into every 32-bit word, waits, and reads every word back.

For each failing word the probe records the byte offset and the bits that differed, so a stuck bit shows as a single mask such as 0x00000020 at a known address.

Probe 3: transformer kernels

Matrix multiply uses the multiply-accumulate units. A transformer block also runs exponentials, divisions, square roots, error functions, sines and cosines, which live on different silicon, and the research says faults are data-dependent: a unit that multiplies correctly can still get a softmax wrong. The kernel probe runs five of them with the device's own kernels, including its attention kernel, and judges every output element the same two ways.

Softmax

Rows of logits. Exercises exp, a sum reduction and a divide. The bound follows the error of each exponential through the sum and the quotient.

Layer norm

Mean, variance, reciprocal square root, scale and shift. The variance allowance is sized for the two-pass, Welford and E[x²]−μ² methods, so a correct implementation of any of them passes.

GELU

The erf form, elementwise. The bound comes from the argument scaling, the erf itself and three roundings.

Rotary embeddings

How most current language models encode token position. The device takes sin and cos of real angles, up to 4,095 radians at the default size, then rotates each pair of values. Large angles test the argument reduction inside sin and cos.

Attention

softmax(QKT/√d)V through the device's fused attention kernel. The bound carries the tensor-core error of QKT through the softmax, allows for the running rescale fused kernels apply block by block, and for P being held in fp16 or bf16. That is why it is the widest.

Every bound on this site follows from one written arithmetic model, recorded in every result file: FP32 arithmetic rounds to nearest, tensor cores accumulate faithfully in FP32, exp, divide and square roots stay within eight ulps, and erf, sin and cos within 2−20 absolute, which admits the shortcut erf that PyTorch uses on ARM processors. Each step also measures the device's own exp, erf, sin and cos on its inputs, so a loose function library can be told apart from a faulty unit. CUDA's own math library documents errors well inside that. A device that breaks the model, or that substitutes an approximate GELU, shows as outside-error-bound on every run, and the message says so. Below the smallest normal value of the output type the bound becomes an absolute floor, because fp16 cannot represent a probability of 10−8 and no chip should be blamed for that.

Probe 6: checksum-protected matrix multiply

Huang and Abraham showed in 1984 that a multiply can check itself. Append to A a row holding its column sums, append to B a column holding its row sums, and one multiply returns C together with C's own row sums and column sums, computed by the same hardware in the same pass. A wrong element breaks exactly one row check and one column check, and where they cross is the element. No reference answer is needed, so the check can run inside real work for the cost of one extra row and column, and it is the design that later becomes a block in silicon.

A' = [ A ; 2⁻ˢ·(column sums of A) ]
B' = [ B , 2⁻ˢ·(row sums of B) ]
A'·B' = [ C , 2⁻ˢ·(row sums of C) ;
        2⁻ˢ·(column sums of C) , … ]

In floating point, rounding makes a correct row sum differ slightly from its checksum, so everything depends on the threshold. Here each threshold is derived element by element from the same arithmetic model as every other bound, and the host removes the known rounding of the checksums exactly, so a correct chip can never cross it. The power of two 2⁻ˢ keeps the checksums from overflowing near the top of the range. The probe also measures its own blind spot: a rectangle of four errors that cancel in every row and column sum is invisible to checksums, so any run the reference check fails while the checksums hold is counted, never passed.

Probe 9: data patterns

Some faults only fire on particular bit patterns, and uniform random inputs almost never produce them. The data pattern probe runs the same matrix multiply, with the same two checks and the same proven or exact reference, on inputs built to reach specific parts of the arithmetic. Every input set is scaled by a power of two where needed, so no partial sum in any order can overflow.

wide
Random exponents across about 80 binades, which exercises the shifters that line numbers up before they are added.
mantissa
Every mantissa bit set to 1, the longest carry chains a multiplier or adder can see.
cancel
Built so the exact answer is zero, so only rounding may remain in the result.
alternate
Checkerboard signs, which make every product in a dot product the same sign, so sums grow to their largest.
sparse
Nine values in ten are exact zeros, for the logic that handles and skips zeros.
subnormal
Inputs below the smallest normal number. The probe first measures, at the step's own shape, whether the chip flushes them to zero, then holds it to the exact model that matches, with no allowance for the other. Shape matters because libraries pick kernels by shape, and kernels differ.
near_max
Scaled so the largest possible sum is a quarter to a half of the output type's maximum.
extremes
int8 only: −128, −127, 0 and 127, the corners of the integer multiplier.

FP8 keeps its inputs in {−1, 0, 1} so its answers stay exact, so it runs the alternate and sparse patterns only.

Probe 11: error counters

A silent error is one the chip does not notice. So every run of the other probes reads the chip's own error counters at its start and its end: ECC counts, remapped memory rows and retired pages, with temperature, clock and power beside them. Then it asks whether the hardware noticed what the probe noticed. Wrong answers with every counter quiet are a silent error in the strict sense, the case ECC and the error logs cannot see. The counters come from NVIDIA's management library, so on other chips the probe records that none are available.

Reading a verdict

Every step ends in one of these words. They are chosen so a reader can tell a chip fault from a software quirk without opening the file.

Compute, kernel, checksum and data pattern probes

no-silent-errors
Every run inside the bound and bit-identical to run 0. The baseline.
silent-data-corruption
Some runs differ from run 0. An intermittent fault, the kind a fleet scanner exists to find.
outside-error-bound
All runs agree with each other but sit outside the proven bound. A faulty unit, a device accumulating below FP32, or for the kernel probe an exp, erf or GELU that is less accurate than assumed.
nondeterministic-kernel
Many runs differ, yet all stay inside the bound. The kernel is not repeatable on that device and precision, so the repeat check cannot be used there. Reported as a finding, not a fault.

Error counters, every run

counters-quiet
No counter moved and every answer was right.
silent-error-confirmed
Wrong answers, and every counter stayed quiet. The hardware did not notice.
hardware-noticed
Wrong answers, and a counter moved too.
corrected-during-run
Every answer was right, but the hardware corrected errors during the run. Worth watching on a healthy chip.
uncorrected-during-run
The hardware recorded uncorrected errors. A fault even if the answers held.

Memory probe

no-memory-errors
Every word read back correctly on every pattern.
memory-errors
At least one word differed. The measurements say which patterns and the log says where.

Self-test

injection-self-test-pass
Every injected fault was caught and nothing else fired. A row is only published alongside one of these.
injection-self-test-fail
The tester missed something it planted. The row is not publishable until that is understood.

Glossary

silent error, silent data corruption, SDC
A wrong result from a chip with no crash, no error flag and no log entry. The chip does not know it happened.
bit flip
One binary digit changing value. In a floating point number a flipped high bit can change the value by orders of magnitude; a flipped low bit changes it by less than one part in a million.
rotary embedding (RoPE)
The way most current language models tell the model where a token sits: each pair of values in an attention head is rotated by an angle proportional to the position, computed with sin and cos.
ECC
Error-correcting code. Extra bits stored with memory that let the hardware detect and usually correct a single flipped bit. ECC covers memory, not the arithmetic units, and not every chip has it on all memory.
HBM
High bandwidth memory, the stacked memory next to a data centre GPU die. An H100 has 80 GB of it.
tensor core
A unit on NVIDIA GPUs that multiplies small matrices in one step. fp16, bf16 and int8 matrix multiplies run through tensor cores; fp32 runs through the regular floating point units.
fp32, fp16, bf16, int8
Number formats. fp32 keeps 24 bits of precision, fp16 keeps 11, bf16 keeps 8 with a wider range, int8 is an exact integer. Models are served in the smaller formats because they are faster, which is why the tester checks all four.
accumulation
The running sum inside a dot product. Even when the inputs are fp16, the sum is normally kept in fp32, which is what the reference bound assumes and what the tester enforces on CUDA.
deterministic kernel
A GPU routine that gives bit-identical output every time for the same input. Not all do, which is why non-determinism is reported as its own verdict instead of as a fault.
reference bound
The largest error that correct rounding can produce for a given computation and precision. Anything larger is a wrong answer. The bound used here is the standard componentwise bound for inner products from Higham.
fault injection
Deliberately corrupting a value to confirm the checks notice. Used here as a self-test on every published row.
dwell
The pause between writing memory and reading it back. Weak cells lose their value over time, so a longer dwell catches more of them.
OCP Test and Validation
The Open Compute Project's open format for hardware diagnostic output, used by cloud operators so that any test's results can be read by any fleet tool. All six probes write it.

EVIDENCE

The self-test

A clean table is only worth something if the tester can show it would have seen a fault. So every row is paired with an injection run.

Compute self-test

In five of the fifty runs, one random bit of one random output element is flipped before the checks run. The bit can be anywhere: sign, exponent or the lowest mantissa bit. All five must be caught. On the chips measured so far, with the v0.2.0 bound, the reference check alone caught 46 of every 60 flips and the repeat check caught all 60. That is why there are two checks.

Memory self-test

After each pattern is written, five random bits in five random words of real device memory are flipped. The sweep must locate all of them by address. Because the flips happen in device memory, this exercises the actual read-back path, not only the comparison code.

EVIDENCE

What a PASS means, and does not

  • It means: no silent error appeared in these matrix multiplies, these checksums, these data patterns, these transformer kernels and this memory sweep, in these runs, on this device, on this day.
  • It does not mean: the chip is healthy. Faults that depend on specific data, on heat, or on hours of load are not yet exercised. The next probes add them.
  • Arithmetic model: every bound assumes FP32 arithmetic that rounds to nearest, tensor cores that accumulate faithfully in FP32, exp, divide and square roots within eight ulps, and erf, sin and cos within 2−20 absolute. A device that breaks the model shows as outside-error-bound on every run, and the message says so.
  • One device per run: links between chips are not yet tested.
  • Self-test scope: the compute injection corrupts the output after it leaves the device, so it proves the checker, not the chip. The memory injection corrupts device memory itself.

Run it on your chip

Ten commands, ten result files, one pull request. Works on CUDA, Apple MPS and CPU today.

# once
git clone https://github.com/tech4biz-yasha/ai-chip-integrity.git && cd ai-chip-integrity
pip install -r requirements.txt

# probe 1, compute, and its self-test
python screen.py --out NAME_clean.jsonl
python screen.py --inject 5 --out NAME_inject.jsonl

# probe 2, memory, and its self-test
python memcheck.py --out NAME_memcheck.jsonl
python memcheck.py --inject 5 --out NAME_memcheck_inject.jsonl

# probe 3, transformer kernels, and its self-test
python kernels.py --out NAME_kernels.jsonl
python kernels.py --inject 3 --out NAME_kernels_inject.jsonl

# probe 6, checksum-protected matrix multiply, and its self-test
python abft.py --out NAME_abft.jsonl
python abft.py --inject 3 --out NAME_abft_inject.jsonl

# probe 9, data patterns, and its self-test
python patterns.py --out NAME_patterns.jsonl
python patterns.py --inject 3 --out NAME_patterns_inject.jsonl
  1. Open a pull request with the ten files, the device name, driver version and PyTorch version.
  2. Rows are added only from attached files. The table is regenerated from them, so a row cannot say more than its file does.
  3. Found a fault? Open an issue with the file. A real finding on real hardware is the most useful thing anyone can contribute.

The output follows the OCP Test and Validation spec v2.0 through the official ocptv library, and the test suite validates it against the published schema.

Roadmap

Twelve probes, each aimed at one part of the chip. Six are built: 1, 2, 3, 6, 9 and 11.

1. Matrix multiplyThree shapes, four precisions plus FP8, a proven or exact reference and a bit-exact repeat check. Done. FP4 once a Blackwell card is measured.
2. Memory pattern sweepSix patterns over most of device memory, exact read-back, address and bit mask on every miss. Done. On-chip SRAM next.
3. Transformer kernelsSoftmax, layer norm, GELU, rotary embeddings and the fused attention kernel against a float64 reference with derived bounds. Done.
4. Full model forward passA small LLM, every layer checked against a CPU float64 reference. Each layer is fed the device's own input, so its bound stays as tight as a single kernel's.
5. Reductions, all-reduce and copy enginesSums across threads, blocks and then GPUs over NVLink and PCIe, with checksums that must agree at both ends, plus copies of known patterns between host and device.
6. Checksum-protected matrix multiplyHuang and Abraham's row and column checksums, which detect and locate a wrong element inside the multiply itself, with proven thresholds and the blind spot measured. Done.
7. Hours under loadThe same probes for hours at full power, with temperature and clocks logged next to every result.
8. Clock and voltage margin sweepLower the margin step by step where the driver allows it and record where each unit starts to fail. Likely needs bare-metal access.
9. Data pattern libraryWide exponents, full mantissas, cancellation, alternating signs, sparsity, subnormals with flush detection, near-overflow and int8 extremes, for the matrix multiply. Done. Patterns for the transformer kernels next.
10. Fault injection inside the computationFlip bits in registers during the multiply to measure how often a flip becomes a wrong answer. The basis for a space radiation column.
11. ECC and error countersEvery run of every probe reads the chip's counters before and after and records whether the hardware noticed what the probe noticed. Done; first real test on the next NVIDIA run.
12. RecoveryAfter a detected fault, reset and rerun on the same card to see whether the fault clears. Likely needs bare-metal access.
Fleet modeRun every probe across many devices automatically and collect the files. Fault rates are per thousand units, so volume is how they get found.
Vendor comparisonRun NVIDIA DCGM and AMD AGFHC on the same device and record what each catches.
